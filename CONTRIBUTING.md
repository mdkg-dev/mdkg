# Contributing to mdkg

Thanks for helping. mdkg is a Rust workspace, pinned to the toolchain in
`rust-toolchain.toml`.

## Build and test

```sh
cargo build
cargo nextest run --workspace
cargo test --workspace --doc
scripts/check.sh
```

The tests run on [cargo-nextest](https://nexte.st): install it with
`brew install cargo-nextest` (or `cargo install cargo-nextest --locked`).
It runs each test in its own process and every binary's tests in one pool,
so a slow binary no longer holds up the ones after it; the profile in
`.config/nextest.toml` keeps going after a failure and kills a test that
runs three minutes without finishing. nextest runs no doctests, so run
those with `cargo test --doc`.

The repository's `affected` rules cover every source file. When adding or
moving one, keep its test-selection rule current; unmapped paths fall back to
the full selection. See [scoping test runs](docs/affected.md).

`scripts/check.sh` is the gate CI runs. It runs:
- `cargo fmt --check`;
- clippy with warnings as errors;
- the tests on cargo-nextest, then the doctests on `cargo test --doc`;
- with mdkg 0.6.0 installed, the checks that 0.6.0 still reads what 0.7
  reads from 0.6 graphs. Point `MDKG_NODE24` at Node 24 and `MDKG_TS_CLI`
  at 0.6.0's `dist/cli.js`; otherwise they're skipped.

The tests need git 2.41 or later, and a git identity (`user.name` and
`user.email`) for the commits they make in temporary repositories.

On Linux, building needs `pkg-config` and the libudev headers
(`libudev-dev` on Debian and Ubuntu, `systemd-devel` on Fedora): the
FIDO2 transport in `crates/mdkg-presence` builds against libudev. CI
installs them on its Ubuntu leg. The tests use a fake security key, so
none needs a real one. Using a real key on Linux needs a udev rule that
gives your user that key's hidraw device alone, as the README says.

## Where things are

| Path | What |
|---|---|
| `crates/mdkg-format` | The file format: parsing, writing, ids and refs. No I/O |
| `crates/mdkg-graph` | Loading, querying and validating a graph |
| `crates/mdkg-log` | The hash-linked event log |
| `crates/mdkg-coord`, `crates/mdkg-coord-sqlite` | The coordinator (leases, claims, settlement) and its SQLite store |
| `crates/mdkg-run` | Waking agents, and `install` |
| `crates/mdkg-cli` | The `mdkg` binary: one module per command group |
| `conformance/` | Fixture graphs and expected results for the format |
| `schemas/` | Every command's JSON output schema, generated by `mdkg schema --out schemas` |
| `spec/` | The Quint model of the lease protocol |
| `docs/format-0.7.md` | The file format spec |

## Rules of the road

- **Only JSON output is a contract.** Each command's `--json` envelope has
  a versioned schema and stable diagnostic codes. Codes are only ever
  added, never reused. After changing an output type or adding a code,
  regenerate `schemas/`; a test fails until you do.
- **Never run a development build against a repository whose coordinator
  matters to you.** A newer build upgrades the store, and an older build
  then refuses it. Test in temporary repositories, as the test suite does.
- **Store migrations are forward-only and additive:** new tables, columns
  or keys, never removed or repurposed ones.
- **No secrets in code, fixtures or logs.**
- Every behaviour change comes with a test that fails without it.

## Pull requests

Keep each change focused, with `scripts/check.sh` passing. The CI workflow
runs it on Linux and macOS, and the release workflow's `plan` job checks
the packaging config.
